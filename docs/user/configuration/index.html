Configuration

nu-agent uses a TOML config file as its sole source of configuration. The Nushell plugin record is no longer supported — all configuration lives in config.toml.

Configuration is organised around three files. Each one lives in its tree's app directory: by default {XDG base}/nu-agent/, or {XDG base}/nu-agent-dev/ in a debug build. An override re-roots the base and the app directory moves with it — see Paths.

FileLocationPurpose
config.toml{config base}/nu-agent/config.tomlMain configuration: models, providers, MCP, compaction, agents, session store
.env{config base}/nu-agent/.env and ./.envOptional environment variables (see Secret Storage)
models.json{data base}/nu-agent/models.jsonLocal cache of the models.dev database

On macOS/Linux the XDG defaults are ~/.config, ~/.local/share, and ~/.cache. If XDG_CONFIG_HOME/XDG_DATA_HOME are set they take precedence, and NU_AGENT_CONFIG_HOME/NU_AGENT_DATA_HOME take precedence over those. Every base, and the nu-agent segment, is described under Paths.

1. config.toml

Location

{config base}/nu-agent/config.toml — $XDG_CONFIG_HOME/nu-agent/config.toml by default. NU_AGENT_CONFIG_HOME re-roots the whole config tree, and a debug build uses nu-agent-dev as the app directory. See Paths for the full ladder.

If the file does not exist, nu-agent uses built-in defaults (plus environment-variable fallbacks — see Environment Variable Fallback). It is not an error for the file to be absent.

Generate a starter config from your current environment with:

agent config init          # creates config.toml (errors if it already exists)
agent config init --force  # overwrite an existing config.toml

agent config init writes a starter file from a built-in template. It never writes a secret: store keys with agent provider auth login <name>. When both AGENT_PROVIDER and AGENT_MODEL are set, it writes that model as the [models.default] line and leaves the rest of the file commented out.

Top-level structure

[models.default]
model = "openai/gpt-4o"

[providers.openai]
api_key = "store:openai"

[providers.openai.models.gpt-4o]

[compaction]
enabled = true
reserve_tokens = 16384
keep_recent_tokens = 20000

[agents]
planner_enabled = true
maker_enabled = true
default = "planner"

Top-level sections:

  • [models.<role>] — per-role model configuration (at least models.default)
  • [providers.<name>] — provider definitions
  • [compaction] — conversation compaction settings (optional)
  • [agents] — built-in persona availability (optional)
  • [session_store] — session store backend (optional)
  • [permissions] — tool execution policy (optional, see Permissions)
  • [mcp] — MCP server definitions (optional, see MCP Servers)
  • [paths] — base-directory overrides for the data, cache, and state trees (optional, see Paths)
  • a2a_enabled — enable A2A (agent-to-agent) protocol (default: false)
  • theme — default TUI theme (optional, see Theme)
  • highlight_languages — languages the transcript renderer highlights (optional, see Highlight languages)
  • [[hooks]] — user hook handlers (optional, see Hooks)
  • cmd_timeout_secs — timeout in seconds for a cmd: reference (optional, see cmd: reference syntax)

Paths

Every path nu-agent touches follows one 4-level ladder per tree, most specific first:

TreeEnv override[paths] keyXDG envDefault under $HOME
configNU_AGENT_CONFIG_HOME—XDG_CONFIG_HOME~/.config
dataNU_AGENT_DATA_HOMEdata_homeXDG_DATA_HOME~/.local/share
cacheNU_AGENT_CACHE_HOMEcache_homeXDG_CACHE_HOME~/.cache
stateNU_AGENT_STATE_HOMEstate_homeXDG_STATE_HOME~/.local/state

The ladder precedence is NU_AGENT_<X>_HOME > [paths].<x>_home > XDG_<X>_HOME > the XDG default under $HOME.

[paths]
data_home = "/srv/nu-agent/data"
cache_home = "~/.cache/nu-agent"
state_home = "/var/log/nu-agent"

The block has exactly three keys: data_home, cache_home, state_home. Rules:

  • No file pins. An override re-roots its whole tree: the tree keeps the {APP_DIR_NAME}/<tail> substructure, so config.toml, .env, agents/, logs/, sessions.db, tool_audit.log, secrets.json, models.json, and theme.json all move with their tree. There is no per-file override.
  • The config tree has no [paths] key. The file that would hold it is the file the ladder has to find first, so the config tree is re-rooted only by NU_AGENT_CONFIG_HOME or an XDG level.
  • One carve-out: the grammar cache. The tree-sitter grammar cache lives at {cache base}/tree-sitter/ — no {APP_DIR_NAME} segment and no -dev split — because the tree-sitter CLI shares that layout. Its base still follows the cache ladder; see Cache path.
  • Relative values are rejected at every level. Env values and [paths] values must be absolute or start with ~; a relative [paths] value is an error at parse time naming the field, and a relative NU_AGENT_*_HOME value is an error during resolution naming the variable. XDG_* variables keep their standard semantics.
  • Unknown [paths] keys are rejected at parse time. A key the block does not define is a hard error that names the key, so a stale key can never silently override nothing.
  • ~ expands to $HOME. Only a leading ~ or ~/ expands. An empty value counts as absent at both override levels, and resolution never creates a directory: the first consumer that writes there creates it.
  • Resolve once, inject. Paths are resolved once at startup by Paths::resolve_for_process, and consumers receive the resolved values — no point-of-use XDG resolution.
  • The -dev split. APP_DIR_NAME is nu-agent-dev in debug builds and nu-agent in release builds. The split applies to every derived path, including the config file's app directory: .env, hooks, and agents/ anchor with it.
  • Hooks stay relative to the config file's dir. A relative script in [[hooks]] resolves against the directory holding config.toml (see Hooks).

Theme

The theme key sets the default TUI theme. Valid values are the four built-in Catppuccin flavors:

theme = "catppuccin-frappe"

Valid values:

  • catppuccin-mocha (default)
  • catppuccin-latte
  • catppuccin-frappe
  • catppuccin-macchiato

An unknown theme value is ignored with a log warning, and the next level in the order below applies. The theme can also be set per-launch with the --theme CLI flag, which overrides the config value; an unknown --theme value is an error. Selecting a theme in the TUI picker persists the choice to $XDG_DATA_HOME/nu-agent/theme.json (mode 0600), which is used on the next launch unless overridden by config or the CLI flag.

Resolution order (highest first):

  1. --theme CLI flag
  2. theme in config.toml
  3. Saved preference file (written by the TUI picker)
  4. Default: catppuccin-mocha

Highlight languages

The highlight_languages key sets the languages the transcript renderer highlights. Code fences, edit diffs, and code cards render token channels for a language on the list. A language outside the list renders plain tokens.

# Absent or empty: the built-in default list.
highlight_languages = []

# Every syntax syntect carries.
highlight_languages = ["all"]

# Exactly these languages.
highlight_languages = ["rust", "python", "nix"]

The built-in default list:

rust, python, go, js, ts, json, yaml, toml, bash, sql, c, cpp, ruby, diff, nu, nix

An entry is a language name or a file extension. An entry the syntax set cannot resolve is logged and skipped.

syntect 5.3 carries no TypeScript or TOML syntax, so ts and toml render plain tokens even under "all". Markdown is in the syntax set but is not on the default list: an edit diff of a .md file renders plain tokens until you add markdown to the list.

max_tokens = 8192
max_context_tokens = 128000

max_tool_result_bytes = 20000
max_tool_calls_per_subturn = 10
read_timeout_secs = 30
max_retries = 3
retry_base_delay_ms = 1000

[models.heavy]
model = "openai/gpt-4o"
temperature = 0.7
max_tokens = 16384
max_context_tokens = 200000

[providers.openai]
api_key = "store:openai"       # vault lookup, env: reference, or omit for the default vault lookup

# per-model overrides (temperature, limits, pricing, name, tool_call, preamble)

The models cache

The local models cache (agent models sync) files each provider's models under its models.dev key. That key often differs from the name you give the block: models.dev files a local Ollama under ollama-cloud, and GitHub Copilot under github-copilot.

catalog is how a block reaches its section. There is no name mapping: a block named ollama reaches no section unless it declares one.

[providers.ollama]
provider = "ollama"
catalog = "ollama-cloud"   # the block now serves the ollama-cloud section

A block that declares a section owns it: the model picker lists every row in that section, and the pricing ladder and the limits fill read the block's rows. A block with no declared section serves only the models it declares, and joins no cache metadata or price for them.

agent models list --provider <name> filters the cache by its own keys, not by config block names, so agent models list --provider ollama lists nothing — the cache has no ollama section. Use --provider ollama-cloud.

Note: The [providers.<name>] block is optional. If omitted, the model is resolved from models.default.model with environment variables as the fallback for API keys and base URLs. Providers that don't require authentication (like Ollama) can be used with just models.default.model = "ollama-cloud/glm-5.2" and no provider block at all.

Model format

All models use provider/model format:

  • ollama/gemma4:31b
  • openai/gpt-4o
  • anthropic/claude-sonnet-4-6

Per-model pricing

A model no shipped catalog prices — a local Ollama classic, a private gateway model — stays tokens-only unless you price it yourself. Set pricing on the model's block:

[providers.ollama.models."llama3.3".pricing]
input = 0.0        # required, USD per million input tokens
output = 0.0       # required, USD per million output tokens
cache_read = 0.0   # optional, USD per million cached input tokens
cache_write = 0.0  # optional, USD per million cache-write tokens

Quote a model id that contains a dot: TOML reads an unquoted models.llama3.3 as the nested keys llama3 → 3.

FieldTypeDescription
inputFloatRequired. USD per million uncached input tokens.
outputFloatRequired. USD per million output tokens, reasoning included.
cache_readFloatOptional. USD per million input tokens read from the cache. Omit it and a call that reads the cache reports a lower-bound cost.
cache_writeFloatOptional. USD per million input tokens written to the cache. Omit it and a call that writes the cache reports a lower-bound cost.

This is the pricing ladder's config outcome, and it wins: a configured price re-prices the model even when its models.dev row lists a cost. The shipped row is the fallback. See Model pricing for the full ladder.

OpenAI-compatible providers

Any provider that implements the OpenAI Chat Completions API (POST /chat/completions) works with provider = "openai" and a custom base_url.

[models.default]
model = "together/meta-llama/Meta-Llama-3.1-70B-Instruct-Turbo"

[providers.together]
provider = "openai"
api_key = "store:together"
base_url = "https://api.together.xyz/v1"

[providers.together.models."meta-llama/Meta-Llama-3.1-70B-Instruct-Turbo"]

This works for Together AI, Groq, OpenRouter, vLLM, LiteLLM, and any other OpenAI-compatible endpoint.

Session store

[session_store]
store_type = "sqlite"    # "sqlite" (default) or "memory"
  • store_type — "sqlite" (default) or "memory"

One backend writes the store: SQLite. It holds every session in {cache}/{APP_DIR_NAME}/sessions.db, or in an in-memory database when "memory" is selected — nothing persists after the process exits there, which is useful for ephemeral sessions and testing. The file has no key of its own: the cache ladder in Paths moves it, and nothing else does.

Precedence for store type: CLI --store flag > AGENT_SESSION_STORE_TYPE env var > config > built-in default (SQLite).

Compaction

[compaction]
enabled = true                   # compact on its own near the window, and after a request the provider refused as too long
reserve_tokens = 16384           # tokens of the model's input limit kept free for the reply
keep_recent_tokens = 20000       # about how many tokens of the newest messages stay as they are

Every key is optional: a key left out keeps the built-in default. The block accepts exactly these three keys, and a key it does not define fails the load as unknown.

Compaction triggers when the tokens the next request would send exceed the model's input limit less reserve_tokens. A model whose input limit is unknown never trips it. A request the provider refuses as too long schedules a compaction for the next request without waiting for the threshold.

  • enabled (bool) — whether a conversation is compacted on its own: near the window, and after a request refused as too long. /compact works either way. Unset = true.
  • reserve_tokens (u64) — tokens of the model's input limit kept free below the trigger: the request fires compaction when it would leave less than this free. Unset = 16384.
  • keep_recent_tokens (u64) — about how many tokens of the newest messages stay as they are; the older ones become the summary. Unset = 20000.

A /compact focus (/compact args) stays reserved: it has no config key and keeps the built-in default.

max_context_tokens lives on the active model role, not in the [compaction] block, but it is the window reserve_tokens is measured against. Set it to match your model's actual context window.

The summarizer is the active model: every compaction call — the threshold schedule and the one /compact asks for — runs on the model the turn sends to, and follows a mid-session model switch. The call is priced at that model's rates.

Agents

[agents]
planner_enabled = true
maker_enabled = true
default = "planner"       # default persona at startup
fallback = "coder"       # optional .agents/<name>.md persona when default built-in is disabled

Defaults: planner enabled, maker enabled, default = "planner", no fallback. fallback is used only when default names a disabled built-in persona and must reference a file under .agents/ or $XDG_CONFIG_HOME/nu-agent/agents/.

A2A

a2a_enabled = true

Enable A2A (agent-to-agent) JSON-RPC 2.0 over HTTP. Default is false.

Hooks

A [[hooks]] entry runs a Nushell script when the agent publishes a lifecycle event. Hooks are observe-only: they never change the turn, the tool result, or the agent output.

[[hooks]]
name = "herdr"
events = ["turn_started", "turn_completed"]
script = "hooks/herdr.nu"
timeout_ms = 5000

Fields:

  • name — required, non-empty. Identifies the hook in log messages.
  • events — required array of event names. An empty array is valid and starts no runner. See Hook events.
  • script — required, non-empty. Path to a Nushell script. A relative path resolves against the directory that holds config.toml; an absolute path is used as written.
  • timeout_ms — optional. Subprocess timeout in milliseconds. Default 10000.

Hook events

Nineteen event names are valid, in two classes.

Session class — per-session events:

  • turn_started
  • turn_completed
  • tool_started
  • tool_completed
  • session_started
  • session_ended
  • permission_requested
  • permission_decision_timed_out
  • permission_decision_submitted
  • permission_decision_ignored
  • permission_request_cancelled
  • permission_auto_resolved
  • compaction_started — fires when a context compaction begins, with its source.
  • compaction_completed — fires when compaction finishes, with a summary preview.
  • compaction_failed — fires when compaction errors, with the message.
  • agent_switched — fires when a user switches the persona, with the slug it left and the slug now active.
  • model_switched — fires when a user switches the model, with the identity it left and the identity now active.

Agent class — per-process events:

  • agent_started
  • agent_shutdown

A hook that declares only session-class events runs on the session hook runner. A hook that declares only agent-class events runs on the process-wide agent hook runner. A hook that declares both runs on both runners. The class is not derivable from the name: agent_switched is session-class because a switch belongs to one session, while the agent_ prefix marks per-process events only for agent_started and agent_shutdown.

The permission_requested event

permission_requested fires when the agent asks the user to approve a tool call. It fires once per prompt, after the agent publishes the request and before the user answers.

The event fires in TUI mode and in ACP mode. It never fires in stderr mode: that mode resolves permissions by policy and never prompts.

Payload fields:

  • request_id — the prompt's identifier.
  • tool — the tool's display name.
  • tool_key — the exact call key, {tool_name}\n{raw_arguments}.
  • source — the tool's source.
  • mode — the call's mode argument, or null.
  • matched_rule_identity — the rule that produced the prompt.
  • scope — the rule's scope.
  • target_field — the argument field the rule matched, or null.
  • pattern — the rule's pattern.
  • summary — the one-line summary shown on the card.

The payload carries no rendered preview. The card's diff preview is a UI artifact and is not part of the envelope.

The switch events

agent_switched fires when the user switches the persona. model_switched fires when the user switches the model. Both fire after the switch took effect, and both carry the session id they belong to.

The events fire in TUI interactive mode, from the agent and model pickers, and in ACP mode, from the client's config options. They never fire in stderr mode, TUI single-turn, or the plugin: none of those has a switch path. In ACP the startup default-agent load is not a switch, and it publishes before the session hook runner subscribes, so no hook observes it.

Payload fields:

  • from — the value in use before the switch. For agent_switched it is a persona slug, or null when the session had no persona. For model_switched it is a provider/model identity and is always present.
  • to — the value now active: the persona slug or the provider/model identity.

Re-selecting the current value still counts as a switch, so the payload reports from equal to to. The envelope's agent and model fields report the post-switch state, because the runner stamps them after the switch.

A persona switch whose model override takes effect emits agent_switched before model_switched on the same channel: two user-meaningful facts changed, so a hook sees two invocations.

The permission_decision_timed_out event

permission_decision_timed_out fires when an unanswered permission card reaches its decision timeout. The agent then auto-denies the call. See decision_timeout_secs under Permissions.

The event fires in TUI mode and in ACP mode. It never fires in stderr mode: that mode resolves permissions by policy and never prompts.

Payload fields:

  • request_id — the timed-out prompt's identifier. It matches the request_id of the earlier permission_requested event for the same card.

The payload carries no tool identity. Correlate with the permission_requested event by request_id.

The permission_decision_submitted event

permission_decision_submitted fires when a decision reaches the permission resolver for a prompted request. It fires once per answered card, before the agent applies the decision.

The event fires in TUI mode and in ACP mode. It never fires in stderr mode: that mode resolves permissions by policy and never prompts.

The event reports every decision that reaches the resolver, whatever its origin. The payload carries no origin field. These all arrive as a submitted decision:

  • the TUI user's answer to the card
  • the ACP client's answer to the session/request_permission prompt
  • an ACP reject-always memory deny, which the bridge answers without prompting
  • the ACP drain-end forced deny, which the bridge answers when the session drains

A request that times out or is cancelled publishes no submitted event. Those paths return before the decision funnel, so permission_decision_timed_out owns the timeout moment and permission_request_cancelled owns the cancel moment.

Payload fields:

  • request_id — the answered prompt's identifier. It matches the request_id of the earlier permission_requested event for the same card.
  • decision — "allow_once", "allow_always", or "deny".
  • matched_rule_identity — the rule that produced the prompt. It matches the matched_rule_identity of the earlier permission_requested event for the same card.

The permission_decision_ignored event

permission_decision_ignored fires when a decision is submitted for a request that is no longer pending. The request timed out, was cancelled, was already resolved, or its turn ended. The agent drops the decision, so the event makes the drop observable.

The event fires in TUI mode and in ACP mode. It never fires in stderr mode: that mode resolves permissions by policy, never prompts, and so has no decision submission path.

Payload fields:

  • request_id — the dropped decision's request identifier. It matches the request_id of the earlier permission_requested event for the same card.
  • reason — why the decision was dropped. The v1 reason set is closed: "request_not_pending" is the only value. Neither emission site can tell a timeout from a cancel from an already-resolved request, so the event states only that the request was not pending.

The payload carries no decision and no tool identity. Correlate with the permission_requested event by request_id.

The permission_request_cancelled event

permission_request_cancelled fires when the turn is cancelled while a permission prompt is open. The agent abandons the pending request and denies the call, so the event makes the abandoned prompt observable.

The event fires in TUI mode and in ACP mode. It never fires in stderr mode: that mode resolves permissions by policy and never prompts.

Payload fields:

  • request_id — the abandoned prompt's identifier. It matches the request_id of the earlier permission_requested event for the same card.
  • matched_rule_identity — the rule that produced the prompt. It matches the matched_rule_identity of the earlier permission_requested event for the same card.

The payload carries no decision: no decision exists at the moment of the cancel. Correlate with the permission_requested event by request_id.

The permission_auto_resolved event

permission_auto_resolved fires when the policy resolves a tool call without prompting the user. The agent then executes the call or blocks it, and the event makes that policy decision observable.

The event fires in all three modes. It is the only permission event that fires in stderr mode: that mode resolves every call by policy and never prompts. In TUI and ACP mode it fires for every call the policy resolves without a prompt; a call the policy sends to the prompt publishes permission_requested instead.

Payload fields:

  • matched_rule_identity — the rule that resolved the call.
  • action — "allow" or "deny".
  • reason — the rule-derived denial reason, or null. It is set only when action is "deny".

The payload carries no tool identity. tool_started precedes this event on the same channel, so a hook correlates by order or subscribes to both events.

Volume and opt-in. The event fires once per policy-resolved tool call: every tool call in stderr mode, and every non-asked call in TUI and ACP mode. A hook that declares it runs a subprocess for each of those calls. The subprocess spawns only when the hook declares permission_auto_resolved in events, so a hook that does not declare it pays nothing. Declare it only for hooks that need the policy decision itself, and keep the handler short.

Validation errors

The agent rejects config.toml at load time when:

  • hooks is not an array of tables
  • an entry has an empty or missing name
  • an entry has an empty or missing script
  • an entry has no events array
  • an event name is not a string
  • an event name is not one of the nineteen names above

The error names the hook and the offending event, and lists the valid names. A hook that fails to resolve at runtime is logged and skipped. Hooks never block a turn.

Permissions

The [permissions] table controls tool execution policy.

[permissions]
"*" = "ask"           # global default
read = "allow"
glob = "allow"
grep = "allow"
edit = "ask"
http = "ask"
skill = "ask"
decision_timeout_secs = 60   # auto-deny an unanswered card after 60s; 0 waits forever

Actions

  • "allow" — execute without prompting
  • "deny" — block execution silently
  • "ask" — prompt the user for approval (TUI mode); deny in non-interactive mode

Global policy

"*" sets the default action for any tool not explicitly listed. Defaults to "ask" (TUI) or "deny" (pipeline) if omitted.

Decision timeout

decision_timeout_secs sets how long an interactive permission card waits for a decision before it auto-denies. The default is 60. 0 waits forever.

A timeout is a denial, not a turn failure: the tool is skipped, the turn continues, and an A2A caller receives a completed task whose answer explains the denial. The timeout applies to every card, including cards from user-submitted turns. Raise the value to read longer, or set 0 to restore wait-forever behavior.

Nested field rules

[permissions.nu.command]
"rm*" = "deny"
"git push*" = "deny"
"*" = "ask"

Precedence

  1. Base config ([permissions] in config.toml)
  2. Agent persona overlay (from persona front matter)
  3. CLI --permissions flag (highest priority)

Safe defaults

When no [permissions] section exists: read, glob, grep → allow; c5t_get*, c5t_list* → allow; ast_query, ast_nodes, ast_refs, ast_tree → allow; nu → ask; the tmux_* tools → ask, except tmux_session with action list or info and tmux_pane with action list, find, process, or capture → allow; everything else → ask (TUI) or deny (pipeline).

Tree-sitter tools (code analysis)

The tree-sitter tools perform structural code analysis using tree-sitter grammars. They are language-generic — they work with any tree-sitter grammar you have installed. They are read-only and auto-allowed by default.

Prerequisites

The tree-sitter tools require the tree-sitter CLI to install and compile grammars. Install it with:

cargo install tree-sitter-cli

Or via your package manager:

# macOS (Homebrew)
brew install tree-sitter

# Debian/Ubuntu
apt install tree-sitter

# Arch
pacman -S tree-sitter

# Windows (scoop)
scoop install tree-sitter

Setup steps

  1. Create the config file (once):

    tree-sitter init-config

    This creates config.json at the platform config location (see below).

  2. Clone grammar repos into a directory you will list in parser-directories:

    git clone https://github.com/tree-sitter/tree-sitter-rust ~/code/tree-sitter-rust
git clone https://github.com/tree-sitter/tree-sitter-python ~/code/tree-sitter-python

  3. Add the directory to the config — edit config.json and add:

    {
  "parser-directories": ["/Users/yourname/code"]
}

  4. Build each grammar:

    cd ~/code/tree-sitter-rust
tree-sitter build

    This creates build/rust.so (or .dylib on macOS, .dll on Windows).

Config file location

The config file is resolved in this order:

OSPath
Any$TREE_SITTER_DIR/config.json (env var override)
Linux$XDG_CONFIG_HOME/tree-sitter/config.json or ~/.config/tree-sitter/config.json
macOS~/Library/Application Support/tree-sitter/config.json
Windows%APPDATA%/tree-sitter/config.json

Config format

The config is a JSON file with a parser-directories array:

{
  "parser-directories": ["/Users/yourname/code"]
}

Any subdirectory of a listed directory whose name starts with tree-sitter- is recognized as a grammar repo. The language name is the suffix — tree-sitter-rust → language rust, tree-sitter-python → python.

Grammar discovery

The tools build a grammar cache on first use:

  1. Reads parser-directories from the config file.
  2. Scans each directory for tree-sitter-* subdirectories.
  3. For each grammar, looks for a compiled shared library in this order:
    1. <grammar_dir>/build/<language>.<ext> — if built in the build/ subdir
    2. <grammar_dir>/<language>.<ext> — grammar dir root (default tree-sitter build output)
    3. <cache_dir>/lib/<language>.<ext> — XDG cache lib/ subdirectory
  4. Loads the symbol tree_sitter_<language> from the shared library.

The cache is built once per process. If you install a new grammar, restart the agent.

Cache path

Compiled grammars are read from the grammar cache at {cache base}/tree-sitter/lib/:

PlatformPath
All platforms{cache base}/tree-sitter/lib/ — $XDG_CACHE_HOME/tree-sitter/lib/ or ~/.cache/tree-sitter/lib/ by default

The cache base follows the cache ladder: NU_AGENT_CACHE_HOME > [paths].cache_home > XDG_CACHE_HOME > ~/.cache under $HOME. See Paths for the ladder rules.

The tree-sitter/ directory keeps no app-dir segment and no -dev split: the grammar cache is deliberately shared with the tree-sitter CLI, which writes the same layout.

Supported languages

ANY language with a tree-sitter grammar. The tools are language-generic — Rust, Go, Python, TypeScript, Nix, TOML, JSON, YAML, and more. Search for grammars at https://github.com/tree-sitter or clone the grammar repo and run tree-sitter build.

Tools

There are four separate tools. Each is called directly with its own parameters — there is no shared action field.

ast_query — run an S-expression tree-sitter query against source code.

  • Required: path, language, query
  • Optional: captures (array of strings), max_matches (int, default 100), include_text (bool, default true)
{"path": "src/main.rs", "language": "rust", "query": "(function_item name: (identifier) @name)"}
{"path": "src/main.rs", "language": "rust", "query": "(struct_item name: (type_identifier) @name)", "captures": ["name"], "include_text": false}

ast_nodes — list AST nodes of a given type in source code.

  • Required: path, language, node_type
  • Optional: max_matches (int, default 200), include_text (bool, default false)
{"path": "src/main.rs", "language": "rust", "node_type": "match_arm"}
{"path": "src/main.rs", "language": "rust", "node_type": "function_item", "include_text": true}

ast_refs — find references to a named symbol in source code.

  • Required: path, language, name
  • Optional: max_matches (int, default 100)
{"path": "src/main.rs", "language": "rust", "name": "Config"}
{"path": "src/lib.rs", "language": "rust", "name": "parse", "max_matches": 50}

ast_tree — dump the full S-expression parse tree of source code.

  • Required: path, language
  • Optional: max_depth (int, default unlimited)
{"path": "src/main.rs", "language": "rust", "max_depth": 3}
{"path": "main.py", "language": "python", "max_depth": 5}

Other languages:

{"path": "main.py", "language": "python", "query": "(function_definition name: (identifier) @name)"}
{"path": "main.go", "language": "go", "node_type": "function_declaration"}
{"path": "default.nix", "language": "nix", "name": "buildInputs"}

2. Secret Storage

The Vault stores all secrets. The Vault is the only interface to secret storage. No other component reads a secret directly.

Startup hierarchy

The Vault probes backends at startup. The first available backend wins. No config section is necessary.

  1. OS keychain — macOS Keychain, Linux Secret Service, or Windows Credential Manager.
  2. File store — a JSON file in $XDG_DATA_HOME/nu-agent/ with 0600 permissions. The agent uses this backend when no keychain is available.
  3. Environment only — no stored secrets. Lookups return nothing. The agent uses environment variables and .env files only.

The Vault always selects a backend. The agent never fails because a keychain is absent.

BackendStorageUse case
KeychainOS credential storeDesktop systems with a keychain
FileJSON file, mode 0600Headless Linux, containers with a mounted data directory
Environment onlyNothingDocker and CI with environment variables only

AGENT_VAULT_BACKEND override

Set AGENT_VAULT_BACKEND to select the backend explicitly. The override replaces the startup hierarchy.

ValueBackend
envEnvironment only. The agent probes nothing.
fileFile store. The agent falls back to environment only when the file store is unavailable.
keychainOS keychain. The agent falls back to the file store, then to environment only, when no keychain is present. A keychain that is present but cannot be opened stops startup with an error that names AGENT_VAULT_BACKEND=file as the escape.
autoThe startup hierarchy. This is the default.

An unknown value logs a warning and uses the startup hierarchy.

Under nextest, the agent selects the environment-only backend when AGENT_VAULT_BACKEND is unset. nextest sets NEXTEST=1 in every test process, and the agent reads that variable as a request for the environment-only backend. An explicit AGENT_VAULT_BACKEND value always wins. Plain cargo test does not set NEXTEST and still probes the keychain.

.env files

The agent loads two .env files at startup, before it reads any environment variable:

  1. $XDG_CONFIG_HOME/nu-agent/.env — user-level, always loaded.
  2. ./.env — project-level, loaded when the file exists.

The loader sets a variable only when the process environment does not already contain it. The loader skips malformed lines and continues.

The order of the two files gives the user-level file priority. The loader reads the user-level file first. Because the loader never overwrites a variable, a key in both files takes the user-level value.

Supported line forms:

# A comment line is skipped
OPENAI_API_KEY=sk-from-file
export ANTHROPIC_API_KEY=sk-ant
QUOTED="value with spaces"
SINGLE='single quoted'

The agent does not support multiline values, escape sequences, or variable interpolation.

store: reference syntax

Reference a stored credential from config.toml with a store: prefix:

[providers.openai]
api_key = "store:openai"

At runtime, the Vault resolves store:openai to the credential for openai. The credential is an API key or an OAuth access token. The syntax is identical for every backend.

env: reference syntax

Reference an environment variable from config.toml with an env: prefix:

[providers.my-gateway]
api_key = "env:MY_GATEWAY_KEY"

At runtime, the resolver reads MY_GATEWAY_KEY from the environment. Use env: for a non-standard variable name. The automatic {PROVIDER}_API_KEY reading (for example OPENAI_API_KEY) needs no env: reference. When the named variable is absent, the resolver sets api_key to None and logs a warning. The resolver never uses the env:VAR_NAME string as a key.

cmd: reference syntax

Run a command and use its stdout as the value. The cmd: prefix works in any string value in config.toml, not only api_key:

[providers.openai]
api_key = "cmd:op read 'OpenAI API Key'"

[mcp.gh.env]
GITHUB_TOKEN = "cmd:gh auth token"

The loader splits the text after cmd: with POSIX word-splitting rules, so a quoted argument keeps its spaces. It runs the command once at load time and substitutes the trimmed stdout. A resolved value is never resolved again, so an output that starts with cmd: stays literal.

The command must exit with status 0 and write a non-empty stdout. Any other result is a hard error at startup. The agent refuses to start and reports the key path, the command, the exit code or I/O error, and stderr. The error never contains the command's stdout.

The default timeout is 30 seconds. Set AGENT_CMD_TIMEOUT_SECS in the environment, or cmd_timeout_secs in config.toml, to change it. The environment variable wins.

The loader runs the command directly, without a shell. It does not interpret Windows shell syntax.

Default vault lookup

Omit the api_key field to look up the credential by provider element name:

[providers.openai]
# no api_key field — the agent looks up provider:openai in the Vault

The resolver looks up provider:<name> in the Vault, where <name> is the providers.<name> element name. When the Vault holds no entry, the resolver leaves api_key as None.

Raw key literals are rejected

A raw key literal in config.toml is a hard error at startup:

[providers.openai]
api_key = "sk-raw-literal"   # REJECTED: not a store:, env:, or cmd: reference

The agent refuses to start and reports: api_key in [providers.openai] must be a store:, env:, or cmd: reference, not a raw value. Use: agent provider auth login openai. Every providers.<name>.api_key value must start with store:, env:, or cmd:, or the field must be omitted.

Precedence

Highest priority first:

PrioritySourceNotes
1CLI flags--api-key overrides all other sources
2Environment variablesSet in the shell, or read from a .env file. Includes {PROVIDER}_API_KEY and env: references
3config.toml api_keyA store:, env:, or cmd: reference. A cmd: reference resolves at load
4VaultResolves a store: reference, or the default provider:<name> lookup when api_key is omitted
5Built-in defaultsHardcoded fallbacks

An environment variable always overrides a stored credential. For example, OPENAI_API_KEY=sk-temp agent run uses sk-temp even when the Vault holds a key for openai.

The agent reads the api_key from config.toml only when no environment variable supplies a key. The Vault does not override an environment variable, because the Vault resolves only the store: reference that config.toml supplies, or the default lookup when api_key is omitted.

Managing credentials

Use the agent provider auth commands:

# Store an API key for a provider (interactive prompt, or via --api-key)
agent provider auth login openai
agent provider auth login openai --api-key sk-...

# GitHub Copilot uses the OAuth device-code flow
agent provider auth login github-copilot

# Clear stored credentials for a provider
agent provider auth logout openai

# Show stored credentials (provider, type, expiry)
agent provider auth status

agent provider auth status outputs one row per stored provider credential. Each row shows the credential type (api_key or oauth) and, for OAuth, the token expiry timestamp.

3. models.json

nu-agent can cache the models.dev database locally to power model discovery, context-window metadata, and the model picker. The cache lives at $XDG_DATA_HOME/nu-agent/models.json.

Syncing

agent models sync

Fetches the latest specs from models.dev and writes them to the local cache. Prints a summary such as Synced 120 providers, 3000 models.

Listing

agent models list                       # all models in the cache
agent models list --provider openai     # only openai models

The plugin command returns one record per model with provider, model, name, context, output, tool_call, input_cost, and output_cost. The cost fields hold the price in USD per million tokens, or null when the cache has no price for the model. The CLI table prints the same rows with PROVIDER, MODEL, CONTEXT, OUTPUT, TOOLS, and COST columns, the price in COST formatted as $3.00/$15.00 (input/output) or - when no price is cached. If the cache does not exist, it instructs you to run agent models sync first.

When a models cache is present, the model picker and resolve_model() use its context/output limits to fill missing max_context_tokens / max_output_tokens values (see resolution priority).

When a provider block's name equals its cache section key (for example ollama-cloud), the model picker lists that section's full model set, with rows the block does not declare rendered unmarked.

Resolution priority

When resolving the runtime config for a model, values are filled from the highest-priority source that sets them, falling through to the next. Highest to lowest:

  1. CLI flags — --model, --api-key, --base-url, --temperature, --max-context-tokens, --max-output-tokens, --max-turns, and --repetition-guard override all config
  2. Persona front matter — a persona's model: field selects a role or literal model
  3. Role-level config — the [models.<role>] record for the selected role (e.g. models.heavy)
  4. Provider/model-level config — [providers.<name>] and [providers.<name>.models.<model>]
  5. models.json cache — fills max_context_tokens, max_output_tokens, and model_context_tokens when not already set by the levels above, and clamps a max_output_tokens above the cache's known output cap down to that cap
  6. Environment variables — AGENT_* vars and {PROVIDER}_API_KEY. A provider or model block overrides an AGENT_* value. {PROVIDER}_API_KEY is the one inversion in this order: it outranks the api_key a provider or model block sets, and it outranks the Vault. Every other key follows the order above
  7. Vault — resolves the store: reference config.toml supplies, or performs the provider:<name> lookup when api_key is omitted. It never overrides an environment variable
  8. Built-in defaults — hardcoded fallbacks

Except for api_key, a value set at a higher priority is never overridden by a lower one. For example, if a role sets temperature, provider-level or env values for temperature are ignored.

Persona model: resolution rules

  1. model: heavy (no slash, matches a role in [models]) → resolves to that role's ModelRoleConfig
  2. model: provider/model (contains a slash) → used as-is as a literal model identifier, with no role-level overrides; the provider block, the models cache, and the environment still apply
  3. model: foo (no slash, not a role) → error at startup
  4. No model: field → falls back to models.default
  5. CLI --model provider/model → overrides everything

Environment variable fallback

Environment variables still work as a fallback when config.toml and the Vault leave a value unset, with one inversion: a {PROVIDER}_API_KEY outranks the api_key a provider block sets.

  • AGENT_BASE_URL
  • AGENT_TEMPERATURE
  • AGENT_MAX_TOKENS
  • AGENT_MAX_CONTEXT_TOKENS
  • AGENT_MAX_OUTPUT_TOKENS
  • AGENT_MAX_TOOL_TURNS
  • AGENT_MAX_TOOL_RESULT_BYTES — max bytes per tool call before truncation (default 20000; 0 = unlimited)
  • AGENT_MAX_TOOL_CALLS_PER_SUBTURN — max tool calls in a single LLM response (default 25; 0 = unlimited)
  • AGENT_MODEL_CONTEXT_TOKENS — approximate context window for token warnings
  • AGENT_CONTEXT_WARNING_THRESHOLD — fraction at which to warn, above 0.0 and up to 1.0 (default 0.6)
  • AGENT_MAX_RETRIES — retry attempts (default 3)
  • AGENT_RETRY_BASE_DELAY_MS — base backoff in ms, doubles each attempt, capped at 30s (default 1000)
  • AGENT_OUTPUT_BUDGET_EMPTY_REMEDY — custom empty-output OutputBudget remedy text (default: built-in empty-output steering)
  • AGENT_OUTPUT_BUDGET_REMEDY_MODE — OutputBudget remedy mode: empty_output or shorter_response (default empty_output)
  • AGENT_OUTPUT_BUDGET_RAISE_ENABLED — opt-in auto-raise of max_tokens on OutputBudget feedback retries (default false)
  • AGENT_OUTPUT_BUDGET_RAISE_MULTIPLIER — multiplier applied to the effective max_tokens for a raised retry (default 2.0)
  • AGENT_OUTPUT_BUDGET_RAISE_CAP — absolute ceiling for the raised max_tokens (default 32768)
  • AGENT_REPETITION_GUARD — enable repetition guard (tool-call + output repetition detection); true/false (default true)
  • AGENT_READ_TIMEOUT_SECS — HTTP read timeout in seconds (default 120). 0 disables.
  • AGENT_A2A_ENABLED — enable A2A (default false)
  • AGENT_SESSION_STORE_TYPE — sqlite or memory
  • {PROVIDER}_API_KEY — e.g. OPENAI_API_KEY, ANTHROPIC_API_KEY (for providers with direct env naming)

There is no AGENT_MODEL env override at runtime; set the default model in config.toml. (agent config init reads AGENT_PROVIDER/AGENT_MODEL when generating a starter config.)

Fixed retry caps

Three turn-executor retry budgets are fixed values. They have no config.toml key, CLI flag, or environment-variable override.

ConstantDefaultBehavior
MAX_PROVIDER_FEEDBACK_RETRIES3Provider feedback retries per user turn for model-correctable failures. Each retry appends one model-facing feedback message to the session memory and re-runs the turn once.
MAX_TURNS_FEEDBACK_RETRIES1Max-turns steering retries per user turn. On tool-call budget exhaustion, the executor appends a steering message and re-runs the turn once with a fresh budget before returning the hard error.
MAX_REPETITION_STOP_RETRIES3Repetition-stop steering retries per user turn. When the output-repetition guard stops the stream mid-turn, the executor converts the stop into a steering retry (steering notice + steering message + escalation-ladder reset); a stop at the retry cap is terminal.

Additional parameters

additional_params forwards a table of provider-specific keys verbatim into the top-level HTTP request body. Set it per role in the model config:

[models.default]
model = "anthropic/claude-sonnet-4-6"

[models.default.additional_params.output_config]
effort = "medium"

Gotchas

  • Only a table carries keys — the value's keys are merged into the top-level request body, so a scalar, a string, or an array has no keys to merge.
  • Do not shadow typed fields — a model, max_tokens, or temperature key here overrides the typed field on the same request and logs a warning. Set the typed field instead.
  • Applied to every turn — the value is included in every completion request.

Controlling thinking depth on Anthropic Sonnet 4.6

Sonnet 4.6 uses adaptive thinking — the model decides when to think. Control thinking depth via output_config.effort:

[models.default]
model = "anthropic/claude-sonnet-4-6"

[models.default.additional_params.output_config]
effort = "medium"

Effort levels: low (fastest, fewest tokens) · medium (recommended for agents) · high (default if omitted) · max (highest capability)
