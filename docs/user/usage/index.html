Usage

Basic

"What is Rust?" | agent

Input can be:

  • plain string
  • record with prompt (and optional context)
{ prompt: "Summarize", context: "short bullets" } | agent

Common flags

# Override model for one call
"quick answer" | agent --model "ollama/gemma4:31b"

# Quiet mode (suppress non-essential progress UX)
"debug this" | agent --quiet

# Progressive verbosity on stderr UX
"debug this" | agent -v
"debug this" | agent -vv
"debug this" | agent -vvv

Tools

# Closure tools
let tools = {
  now: {|| date now | format date "%Y-%m-%d %H:%M:%S" }
}
"what time is it" | agent --tools $tools

Agent personas

Load instructions and configuration from persona files using --agent:

"implement the feature" | agent --agent coder

Persona file resolution (first match wins):

  • .agents/<name>.md (project-local)
  • $XDG_CONFIG_HOME/nu-agent/agents/<name>.md (global, usually ~/.config/nu-agent/agents/)

NU_AGENT_CONFIG_HOME re-roots the global candidate with the whole config tree; a debug build uses nu-agent-dev as the app directory. See Paths.

Front matter keys (optional YAML)

---
name: coder
description: Development agent focused on implementing features
model: anthropic/claude-sonnet-4-20250514
temperature: 0.2
max_tokens: 8192
max_tool_turns: 20
max_tool_calls_per_subturn: 3
max_tool_result_bytes: 50000
additional_params:
  thinking: disabled
permissions:
  "*": "ask"
  "read": "allow"
  "c5t_get*": "allow"
---

# Your agent instructions here

All front matter keys are optional:

  • name — agent identity (overridden by --name flag)
  • description — persona summary shown in agent list
  • model — model role name or literal provider/model (resolved via models map; overridden by --model flag)
  • temperature — response creativity, 0.0–2.0 (overridden by --temperature flag)
  • max_tokens — maximum tokens to generate
  • max_tool_turns — maximum tool execution turns per conversation turn
  • max_tool_calls_per_subturn — maximum tool calls per LLM sub-turn
  • max_tool_result_bytes — maximum bytes per tool result before truncation; 0 = unlimited
  • additional_params — provider-specific parameters (e.g. thinking: disabled for Anthropic)
  • permissions — authorization overlay (overridden by --permissions flag)

Precedence: CLI flags > front matter > config.toml

Examples

# Use persona as-is
agent --agent researcher

# Override persona's model
agent --agent coder --model openai/gpt-4o

# Override persona's name
agent --agent coder --name "bob"

Model roles

Configure named model roles in config.toml:

[models.default]
model = "openai/gpt-4o"

[models.heavy]
model = "anthropic/claude-sonnet-4-6"

Then reference roles by name in agent persona front matter:

---
model: heavy
---

When a persona's model names a role you defined (no slash), it resolves to that role's model from config.toml. If your persona needs a specific model that isn't in the map, use the full provider/model identifier instead:

---
model: openai/gpt-4o-mini
---

CLI --model provider/model overrides all resolution and is used as-is.

Resolution rules:

  1. Role name (e.g. model: heavy, no slash, matches a key in models) → resolves to that key's value
  2. Literal (e.g. model: provider/model, contains slash) → used as-is
  3. Unknown role (no slash, not in the map) → error at startup
  4. No model: field → falls back to models.default

Model pricing

Every model the runtime can serve resolves a price through one ladder. The ladder runs once, when the model binding is constructed, and the resolved prices ride the model's wire facts. The cost hook reads them; it holds no rung logic of its own.

Outcomes, highest precedence first:

  1. Endpoint-reported — the provider's own reply states the cost. This is authoritative and always wins.
  2. User-configured pricing — a pricing block on the model's config record. The user stated what they pay, so it wins over the shipped rate. See Per-model pricing.
  3. Own cache row — the model's own row in the local models cache (agent models sync) lists a cost.
  4. Residual — nothing prices the model. The call stays tokens-only.

The cache row reads the same cache the model picker renders, so the price a session computes and the price the picker shows come from one source.

There is no cross-vendor borrowing: a model id priced only under another section stays tokens-only unless the block declares that section as its catalog.

Pricing is per model id, not per wire. The vendor whose wire serves the model scopes only the base spec's shape — the modalities and compatibility the built-in model catalog lists for that vendor. The price comes from the ladder over the models cache, keyed by the model id and the block's declared cache section. A provider block named for a reseller therefore prices from the section it declares: a block named ollama-cloud that serves through the openai wire (provider = "openai", base_url = "https://ollama.com/v1") prices its models from the ollama-cloud section, even though the wire reports openai.

Provider names and the cache

The cache stores models.dev provider keys. A config block reaches its section through catalog; without it, the block name is its own section key. There is no name mapping, so a block named ollama reaches no section unless it declares catalog = "ollama-cloud". See The models cache.

The Ollama caveat

ollama reaches no cache section, so its models stay tokens-only. Declare catalog = "ollama-cloud" and the block prices from that section, whose rates are Ollama Cloud list prices for those model ids. A local Ollama server is not billed those rates, so the session cost line then reads as if the tokens were billed at cloud list prices.

The residual

A model no rung prices stays tokens-only. The existing signals say so explicitly: the model picker leaves its price column blank, and the session cost line shows tokens alone, or a figure ending in + while any call was unpriced. The residual classes are:

  • a model id the cache lists with no cost — a local Ollama classic whose id no hosted vendor uses is the common case;
  • a model the cache does not list at all, or one whose block declares no catalog and whose name is not a cache section key.

A blank price is never invented. If a model you use lands in the residual, run agent models sync first — a newer cache may price it — or set a pricing block for it in config.toml.

A reply that reports no input or output token count also stays tokens-only: the rates apply to those counters. A missing total_tokens never blocks a price — some endpoints omit it, and the total is not what the rates multiply.

A session whose calls are only partly priced shows the summed price with a + suffix. That happens when a call reports cache tokens the model's row lists no rate for: the known parts are summed, and the + says the figure is a lower bound.

What the status bar's figures measure

The two figures the status bar shows side by side carry different scopes. The token figure — 12.3k, with a percent of the context window beside it when the model reports a window — is the arriving session's history: what that session's own turns reported, placed by the replay when the surface switches into it. The dollar figure after the · is cumulative across sessions on this surface: a session switch and /new both leave it alone, and only a live priced call adds to it. A replayed history's calls carry no price, so switching into one puts the + lower-bound marker on the figure; the marker adds no money. Switching into the same history repeatedly adds nothing to and removes nothing from either figure: the token figure re-places, the dollar figure holds.

Syntax highlighting

Code fences, edit diffs, and code cards render token channels for the languages on the highlight list. A language outside the list renders plain tokens.

The built-in list covers rust, python, go, js, ts, json, yaml, toml, bash, sql, c, cpp, ruby, diff, nu, and nix. Widen or narrow it in config.toml:

# Every language syntect carries.
highlight_languages = ["all"]

# Or exactly these.
highlight_languages = ["rust", "python", "markdown"]

See Configuration for the full rules.

Tool authorization (permissions DSL)

Authorization uses a map-style permissions DSL (not a rules array).

Only CLI surface for policy override is --permissions (structured record/object).

# Build per-run overlay in Nu and pass as a record
let permissions = {
  "read": "deny"
  "nu": {
    "command": {
      "kubectl delete *": "deny"
      "*": "ask"
    }
  }
}

"review this command" | agent --permissions $permissions

Canonical shape:

[permissions]
"*" = "ask"
read = "allow"
"c5t_get*" = "allow"

[permissions.nu.command]
"kubectl delete *" = "deny"
"*" = "ask"

Supported values

  • global baseline: "*": "allow|ask|deny"
  • tool pattern actions: "read": "allow", "c5t_get*": "allow"
  • nested nu map with explicit command key only:
    • "nu": { "command": { "<pattern>": "allow|ask|deny" } }

Unknown nested fields under nu are rejected with deterministic diagnostics.

Deterministic precedence

Decision order is fixed:

  1. global baseline
  2. tool override
  3. nested nu.command override

For nu.command matching, runtime normalizes commands by:

  • trimming leading/trailing whitespace
  • collapsing internal whitespace runs to one space

If nu.command is missing/unreadable, behavior deterministically falls back to inherited tool/global decision with diagnostic metadata.

If nested "*" equals inherited decision, it is a valid no-op and reported via deterministic diagnostics metadata.

CLI overlay merge semantics

Effective policy is built once at startup using additive overlay:

  1. base: config.agent.permissions
  2. overlay: CLI --permissions

Merge rules:

  • overlapping leaf/action keys: CLI wins
  • non-overlapping config keys: retained
  • nested maps (for example nu.command): deterministic key merge

Malformed CLI overlay fails fast with explicit key-path diagnostics.

Startup emits a compact policy diagnostic summary:

  • permissions policy: overlay_active=true|false global=<action> tool_rules=<n> nu.command_rules=<n>

Ask flow and session grants

Ask hook choices are:

  • allow_once
  • allow_always (session-only; reset on restart)
  • deny

allow_always grants are session-only and scoped to the approving tool context (tool/source/mode scope), not global across unrelated tools.

Within a running session, later calls in the same scoped tool context can reuse that grant. Restarting the plugin/session clears all allow_always grants.

Interactive permission prompt behavior (TUI)

When a tool call resolves to ask in TUI mode, execution pauses at the authorization boundary until a decision is submitted. The tool handler is not invoked while waiting.

The permission ask UI is rendered as a compact inline permission card attached to the active tool call display in transcript space (not a large blocking modal).

The card includes request context (tool, source, optional mode), matched rule metadata, summary, and request_id.

Exact keybindings:

  • a => allow_once
  • A => allow_always (session-only)
  • d => deny

Esc is not a card key. With a card up, Esc behaves as usual: in insert mode it exits to normal mode, and in normal mode it arms the turn-cancel confirmation. The card stays up while the confirmation is armed; a confirmed cancel auto-denies the pending request and closes the card.

Safety semantics:

  • Decision timeout: an unanswered card auto-denies after decision_timeout_secs (default 60s, 0 waits forever); the tool is skipped and the turn continues
  • Stale/unknown decision submissions => ignored
  • Rule-identity mismatch submissions => ignored
  • Prompt handling remains deterministic and non-blocking for overall UI loop

TUI rendering guardrails:

  • Prompt content is rendered as an inline transcript card anchored to the related tool row (not a blocking modal).
  • Permission decision controls are rendered in a sticky footer row so controls remain visible independent of transcript window clipping.
  • Viewport fitting preserves a required permission-context row while ask is active; manual user scroll override disables auto-recentering jitter but keeps required-row preservation state.

Transcript gutters (columns are list-local; column 0 is the transcript list area's first column):

  • User messages render a dotted ╎ rail at column 0 on the first row and on every wrapped row; the text starts at column 2 (the cog column).
  • Assistant prose starts at column 2 and carries no rail.
  • Tool, compaction, and system rows keep the two-column cursor slot: the marker glyph (⚙, ~, ·) sits at column 2 and the text starts at column 4, on the first row and on every wrapped row.
  • The banner stays centered within the pane.
  • Every entry keeps a two-column right margin: the wrap budget stops short of the list area's right edge, so no line writes into its last two columns. A painted surface — the user turn's background or a display's code surface — still spans the full list width.

Nu command rendering:

  • Each tool call row starts with the tool name (for example edit, read, nu) followed by the call summary. The name carries the tool lane's emphasis style; the summary carries the muted style. The nu call line carries the applied timeout as ⏱ {timeout}s (120s when the call omits timeout_seconds) — the command renders only in the entry's display body below it.
  • A tool call is one transcript entry for its whole life. The entry holds a gate preview and a completion result, and the body renders whichever is present, result.or(preview). A body carrying code or diff content paints on the code surface with one blank padding row above and below, inside the entry's own rect: the command or the diff is never a companion block, and the call row never carries a background or a margin row.
  • When the agent calls the nu tool, the command renders as a syntax-highlighted block (language nu) under the tool row. While the call waits at the permission gate the body is the preview, built from the tool-call arguments alone — nothing executes before you approve. The preview arrives before the decision; at completion the result takes over the same slot, and the preview persists when the completion carries no display.
  • The edit tool's diff display renders in the same code surface. Each diff body line carries a muted line-number gutter (old and new columns) followed by the syntax-highlighted code body, on a line-level tint: added lines get a dim green background, removed lines a dim red one, and context lines stay untinted. Hunk headers (@@), file headers (---/+++), and the no-newline marker render as plain meta rows.
  • Consecutive tool entries carry no separator row: a tool entry is flush, so the displays' own padding rows supply the spacing. A tool entry next to assistant prose keeps one separator row, in either order. A padding row on the frame's first or last row is clipped, so the frame opens and closes on content rows.
  • Other tools keep their existing previews (edit shows a diff, nu shows the command) or none.
  • See docs/contribution-guardrails.md for the pre-authorize zero-write rules behind the edit preview.

Lifecycle events emitted by runtime/UI path (all delivered on the single ui_event bus channel):

  • PermissionRequested
  • PermissionDecisionSubmitted
  • PermissionDecisionTimedOut
  • PermissionDecisionIgnored
  • PermissionRequestCancelled
  • PermissionAutoResolved

Non-interactive ask fallback

In non-interactive mode (stderr mode), a tool call the policy marks ask resolves to deny. No prompt is shown, the tool is skipped, and the turn continues.

There is no separate key for it: ask is a policy action everywhere, and the non-interactive resolver converts it to deny. To allow a call in that mode, allow it in the policy itself:

[permissions]
"*" = "allow"
  • fallback (policy action ask): deny
  • to allow a call: an explicit allow on the tool, or on "*"
  • an invalid action value is reported as a diagnostic and ignored, so the rest of the policy stays in force

Built-in tools

The agent exposes the following built-in tools (no MCP server required):

Filesystem (CAS-safe):

  • read — read file content with optional line windowing
  • edit — search/replace or create files with CAS guard

Search:

  • grep — recursive regex search (ripgrep-style)
  • glob — file glob matching

HTTP:

  • http — fetch URLs, markdown extraction from HTML

Skills:

  • skill — load skill content by name from local or home skill roots

Shell execution:

  • nu — stateless Nushell command execution (NOT bash/sh/zsh)

Code analysis:

  • ast_query — run an S-expression tree-sitter query against source code

  • ast_nodes — list AST nodes of a given type in source code

  • ast_refs — find references to a named symbol in source code

  • ast_tree — dump the full S-expression parse tree of source code

    All four tools require path and language parameters. language must match an installed tree-sitter grammar (e.g. rust, python, go). See Configuration for full setup instructions.

    {"path": "src/main.rs", "language": "rust", "query": "(function_item name: (identifier) @name)"}
{"path": "src/main.rs", "language": "rust", "node_type": "function_item"}
{"path": "src/main.rs", "language": "rust", "name": "Config"}
{"path": "src/main.rs", "language": "rust", "max_depth": 3}

tmux session management:

  • tmux_session — list, info, create, kill sessions
  • tmux_window — create, kill windows
  • tmux_pane — list, find, capture, send, split, kill panes
  • tmux_layout — select layout

Panes are addressed as session:window.pane. Prefer the target field returned by tmux_pane list/find; pane: "2" means pane index 2 of the given (or current) window, not window 2.

These names are unprefixed and exact. There are no builtin aliases like fs__read or tool__edit.

Filesystem tool permission gating

read is non-mutating and bypasses the permission system entirely — it is always allowed.

edit is filesystem-mutating and requires permission approval, exactly like MCP or closure tools. Use the permissions DSL to control its behavior per persona:

# Developer persona — allow edit without prompting
permissions:
  "*": "ask"
  "edit": "allow"
# Researcher persona — deny all writes
permissions:
  "*": "ask"
  "edit": "deny"
# Default (safe) — prompt before every edit
permissions:
  "*": "ask"

Via CLI:

# Allow edit for this run
let perms = { "*": "ask", "edit": "allow" }
"refactor the code" | agent --permissions $perms

The default for unmatched tools is ask (interactive prompt in TUI, deny in non-interactive mode).

Contracts

  • read is non-mutating and returns file content plus metadata, including version (content hash token).
  • edit is a mutating operation and requires expected_version.
  • expected_version is compared against the current file version (CAS guard) to prevent blind overwrites.

read example

{
  "tool": "read",
  "arguments": {
    "path": "src/lib.rs",
    "offset": 0,
    "limit": 120
  }
}

Typical response fields:

  • content
  • total_lines
  • offset
  • limit
  • version

edit canonical contract (preview/apply)

edit uses a single stable contract with explicit mode:

  • mode: "preview" computes validation + planning + diff without writing.
  • mode: "apply" uses the exact same validation + planning semantics, then writes if allowed.
  • The operation block is required and supports types search_replace or create.

Canonical request shape:

{
  "tool": "edit",
  "arguments": {
    "path": "src/lib.rs",
    "mode": "preview",
    "expected_version": "<version-from-read>",
    "operation": {
      "type": "search_replace",
      "search": "old_name",
      "replacement": "new_name",
      "match_mode": "literal",
      "occurrence": "first"
    }
  }
}

Stable response envelope fields:

  • proposal_id (currently null in this slice)
  • applied (bool)
  • would_change (bool)
  • diff (deterministic diff text for this plan)
  • stats (deterministic counters)
  • diagnostics (deterministic class/message entries)

Diff/newline semantics:

  • Diff rendering is deterministic for identical input snapshots and operation plans.
  • Paths in diff headers are stable (--- a/file, +++ b/file) for edit contract parity between preview/apply.
  • Newline model preserves source line endings (LF/CRLF) in emitted line payloads.
  • EOF newline transitions use unified-diff marker \\ No newline at end of file.
  • Large diff output is bounded and can include a truncation marker with omitted-count metadata while preserving full summary stats.

Deterministic diagnostic classes used by the edit contract:

  • validation
  • stale
  • permission
  • conflict
  • internal

No-op and conflict results:

  • An apply-mode edit that would not change the file fails the tool call. The tool returns an error whose message names the reason (no change for an unmatched search or an identical replacement, conflict for a stale expected_version or an existing create target) and whose details carry the same contract envelope (applied: false, would_change: false, noop or conflict: true, diff: "").
  • The permission gate shows no diff block for these plans — there is nothing to approve, so the prompt renders bare.
  • The failed disposition marks the tool row as failed in the TUI instead of done.

edit with operation.type: "create" (new file creation)

To create a new file, use operation.type: "create" with a content field:

{
  "tool": "edit",
  "arguments": {
    "path": "src/new_module.rs",
    "operation": {
      "type": "create",
      "content": "// New module\npub fn hello() {\n    println!(\"hello\");\n}\n"
    }
  }
}

Notes:

  • expected_version is not needed for create operations.
  • If the file already exists, the call fails with an already exists conflict error. Use search_replace instead.
  • Parent directory must exist. The tool does not create intermediate directories.

CAS conflict recovery flow (required)

When edit detects a version mismatch, do not retry with stale args. Use this flow:

  1. read the file again to get latest content and version
  2. recompute your intended change against that latest content
  3. retry edit with the new expected_version

Short form: read -> recompute change -> retry with latest version.

This is the required conflict recovery pattern for all mutating filesystem built-ins.

Session storage

A session's conversation lives in the session store. The --store flag picks the backend:

--storeWhere the session lives
sqlite (default){cache}/{APP_DIR_NAME}/sessions.db — one database holds every session
memoryAn in-memory database. Nothing survives the process, so it is for tests and one-shot runs

APP_DIR_NAME is nu-agent-dev in debug builds and nu-agent in release builds. One backend writes the store: SQLite, in a file or in memory. Pointing an unsupported store name yields an Invalid --store value error.

A stopped or failed turn keeps its completed work. A turn is saved only when it succeeds, so the host appends the interrupted turn's delta to the session log itself: the prompt, the tool exchanges that finished (with their real results), and the assistant text the turn streamed. A call killed mid-execution is closed as [interrupted], so the log stays valid. The next turn continues from that log. A call the stop denied before it ran renders as a not-run (⊘) tool block with the args preview of what would have run under it, live and after a reload. No reason text renders. The batch's later calls the stop skipped without dispatching render the same ⊘ shape. A nu command the wall clock kills (timeout_seconds elapsed) or the turn's cancel stops renders that same ⊘ block with the command preview, live and after a reload; the model still receives the timeout or cancel as an error.

The status of every call is stored with the session, as a variant: success, failure, or cancelled (the one class every non-completed call falls in). A reloaded row renders the status the store holds, not one re-read from the result text, so the timeout, the user's cancel, and a call the stop never dispatched all rehydrate as the same ⊘ block. Sessions saved before the status was stored keep the verdict their is_error flag carries — a failed call renders ✕, a successful one ✓.

Resuming replays the session. Attaching to a session projects its stored messages onto the same event log a live turn produces and folds them through the same reducer. The transcript rows, the tool statuses and their displays, the usage counters, and the compaction bookkeeping are therefore the state the live session ended in — a resumed session and a running one cannot disagree. The stored messages, not the rendered rows, are the source: the transcript is rebuilt, never re-parsed. A stored role outside the known set carries no transcript row and is skipped.

A warning appears when the turn's work could not be saved. If another writer moved the session log while the turn ran, the host leaves the log alone and shows "Turn stopped: the session log moved mid-turn; this turn's work was not saved" instead of writing a delta it cannot attribute.

Stopping may take up to ~2 s. After a cancel, the turn keeps draining the model stream for a bounded grace so in-flight tools finish and their results reach the session log.

Re-login when the Copilot credentials do not load. A stored Copilot login lives only in copilot.json in the Copilot credential directory. A login stored anywhere else is not picked up; run agent provider auth login github-copilot again.

Session metadata

The host writes the session's state records itself:

  • rig::model — the provider/model string the turn ran, taken from the resolved config rather than the wire descriptor (a custom provider on an OpenAI-shaped wire would otherwise be mislabelled).
  • rig::title — the start of the session's first user message, so a resumed session keeps its original title.
  • meta.json — the listing: title, labels, updated, model, message count, and plugins' listed values.

A model switch rewrites the model record and relists; it passes no title, so the title is preserved.

agent session list and agent session inspect read these records. The plugin command shows all seven listing fields (id, title, model, messages, updated, labels, listed — listed as JSON text). The CLI's agent session list table shows five of them (ID, TITLE, MODEL, MESSAGES, UPDATED): labels and listed are plugin-owned metadata, so the CLI table leaves them out. Use the plugin command when you need them.

A session whose store cannot be opened is skipped with a warning, so one unreadable log does not hide the others.

Open-store bound

A session's store is opened on first use and kept. At most 32 stores stay open at once; the oldest is dropped when the bound is reached. A turn that still holds the store keeps it alive through its Arc, and the next access reopens it.

On the memory backend nothing persists across opens, so an evicted session disappears from agent session list entirely — its conversation lived only in the store that was dropped.

Compaction triggers and persistence

  • Auto compaction fires when the next request would exceed the model's input limit less reserve_tokens: 16384 tokens (unset) or the count you set.
  • A request the provider refuses as too long schedules a compaction for the next request, without waiting for the threshold.
  • Manual slash trigger:
    • /compact triggers force compaction immediately (bypasses the threshold gate)
    • /uncompact restores what the most recent compaction replaced (with nothing to undo it warns and changes nothing)
    • /compact <args> is treated as unknown for now
    • unknown slash commands emit a warning and processing continues
  • Slash command text is runtime control input and is not forwarded as prompt text to the LLM.
  • Manual and auto trigger sources share one execution path, and compaction persistence is durable:
    • the splice is written to the session's saved memory
    • the compacted message set is what the next run loads
    • transcript-visible compaction summary artifact includes source + summarized counts
    • compaction summary artifact includes summary preview/body from the produced summary text
    • the real token count resets after a compaction, so the next turn estimates from the summary until its first completion reports a counted total

Compaction settings

The [compaction] block has three keys. Every key is optional: a key left out keeps the built-in default.

keytypemeaningunset

The behavior those keys shape:

  • The newest messages stay as they are within the keep budget; the older ones become the summary.
  • A short conversation is still summarized when /compact asks for it.
  • A second compaction updates the previous summary rather than replacing it with an unrelated one.

The block reference lives in Configuration.

CLI flags override config.toml, which overrides built-in defaults.

Inline slash suggestions and slash commands

  • Inline slash suggestions open immediately when input starts with /.
  • Suggestions are non-modal and independent of command palette popup/table/state.
  • Filtering is deterministic and incremental as input grows (/c, /co, ...).
  • If slash prefix is removed, inline suggestions close cleanly and never fallback to command palette.
  • Up and BackTab move the suggestion highlight up, and Down moves it down.
  • Tab and Enter both accept the highlighted suggestion and submit it; the accepted command is not echoed into the transcript.
  • Esc closes the suggestion list.
  • Supported slash commands:
    • /compact
    • /uncompact
    • /mcp
    • /help
    • /status
    • /skills
    • /models
    • /agent
    • /new
    • /session
    • /theme
    • /stats
  • /help, /status, /mcp, and /skills route to the same action handlers as Ctrl-P entries.
  • /models and Ctrl-P Models route to the same shared model-picker action handler.
  • /stats toggles the render-stats band: it sits under the status line at the screen bottom, two rows tall — a data row of counters plus a legend row decoding them — never covers the input box, the status line, or the transcript, and only /stats turns it on or off.
  • /new clears the transcript, starts a new session, and shows the startup logo.
  • /new and a session switch both settle the display the session that left was showing: the status line, an open permission card, the compaction display, and a stranded busy phase do not cross the boundary into the session that arrives. A turn still running keeps its own display.
  • While a turn runs, /new, a model switch, and an agent switch apply when that turn finishes, and the status bar says so when the command arrives.
  • Unknown slash commands emit deterministic warning text and the interactive loop continues.
  • Immediate slash command text is not echoed into the transcript and is not persisted as a session turn message.
  • Compaction result artifacts remain transcript-visible (for example, compaction summary/source/count rows).
  • Input soft-wraps at word boundaries; the input box grows up to 6 rows, then scrolls internally keeping the caret visible.
  • The input caret is a buffer cell, not the terminal cursor. Insert mode paints a ▏ bar in the input text style; normal/visual mode reverses the character under the caret. The terminal cursor stays hidden, so the caret does not flicker when the pane repaints.
  • A modifier+letter key with no binding never inserts text: Ctrl/Alt/Super+letter (for example Ctrl-F, Alt-B) leaves the input unchanged, while Shift+letter still types the capital and the bound Ctrl letters (Ctrl-C, Ctrl-U, Ctrl-D, Ctrl-P, Ctrl-N, Ctrl-J, Ctrl-K) keep their actions.

Prompt queue and cancel-on-empty-Enter

  • Submitting a prompt while a turn is busy queues it; the queued prompts run after the active turn completes.
  • Typing while a turn is busy edits the draft: characters, Backspace, Delete, and Alt-Enter/Shift-Enter newlines reach the input box, and Enter queues the prompt instead of dropping it. A bracketed paste while a turn is busy is still dropped.
  • Queued prompts render as one merged user-message block stacked directly above the input box: a tinted padding line above and below the text, a continuous ╎ gutter down every row with no separators between messages, and one blank row separating the block from the transcript. Text wraps at the transcript user-message width, so the stack's rail and text columns match the transcript user rows.
  • The queue drains as one submission, and that submitted block renders the same one-row-per-message rhythm as the stack — no blank line between the coalesced prompts.
  • Pressing Enter on empty input while a turn is busy and at least one prompt is queued cancels the active turn. The queued prompts then run through the normal drain path.
  • Pressing Enter on empty input while idle, or while busy with no queued prompts, does nothing.
  • Stopping a turn shows Turn stopped in the status bar until the next turn starts or the surface moves to another session, and keeps the turn's completed work in the session.
  • Esc while a turn runs arms the cancel confirmation (Esc again to cancel); a second Esc cancels the turn. While a picker or an info panel is open, Esc closes it and does nothing else: the next bare Esc arms the confirmation. The arm lives exactly as long as its message — once the message expires, the next Esc arms again instead of cancelling.
  • If the turn finishes between the two presses, the next Esc shows turn already finished — nothing to cancel instead of silently toggling the input mode. The notice appears once and expires through its own TTL.

Ctrl-C quit guard

  • Ctrl-C is intercepted globally, before any popup or mode routing. Each press does exactly one thing.
  • A permission prompt open: Ctrl-C arms the quit confirmation and leaves the prompt untouched. d owns deny; with a card up, Esc behaves as usual (mode exit, or arms the turn-cancel confirmation). A confirmed cancel auto-denies the pending request and closes the card.
  • Any other popup open (picker, info panel, inline slash): Ctrl-C closes it without arming and without changing the draft.
  • No popup and a non-empty draft: Ctrl-C clears the draft without arming. The turn state is unchanged, so a busy turn keeps running.
  • No popup and an empty draft: Ctrl-C arms the quit confirmation and shows Ctrl-C again to quit.
  • A second Ctrl-C within 5 seconds quits. While a turn is busy, quitting also requests cancel.
  • Any other key or a paste disarms the confirmation. A resize leaves it armed.
  • The confirmation expires after 5 seconds; the status message expires through its own 5 second TTL.

Hooks

A hook is a Nushell script that runs when the agent publishes a lifecycle event. Hooks observe the agent. They never change a turn, a tool result, or the agent output.

Configure hooks in config.toml. See Configuration § Hooks for the fields.

[[hooks]]
name = "herdr"
events = ["turn_started", "turn_completed"]
script = "hooks/herdr.nu"

Handler convention

The agent runs one handler per event. The handler is a function named after the event. It takes one argument: the envelope as a record.

def turn_started [event: record] {
    print $"turn started in session ($event.session_id)"
}

The agent invokes the handler with this command:

nu --stdin -c "source '<script>'; <event> ($in | from json)"

The agent writes the JSON envelope to the child process stdin. --stdin binds that input to $in, and from json turns it into the record the handler receives. The handler runs in the session working directory and inherits the environment.

Envelope

Every invocation receives one JSON envelope:

{
  "version": 1,
  "event": "turn_started",
  "timestamp": "2026-10-25T14:32:07.481920+00:00",
  "session_id": "9dad1e4e08b0b11c-main",
  "agent": "planner",
  "model": "openai/gpt-4o",
  "payload": {
    "prompt": "list the rust files",
    "task_id": null
  }
}
  • version — envelope schema version. Current value is 1.
  • event — the event name.
  • timestamp — RFC 3339 UTC time of the invocation.
  • session_id — the session the event belongs to. See Session id.
  • agent — the persona slug in effect when the invocation was built. A string, or null when no persona is loaded. A handler reads it as $event.agent.
  • model — the active model identity, as provider/model.
  • payload — event-specific fields.

agent and model are additive observability fields. version remains 1, so a handler that reads only the five original keys keeps working.

The runner stamps both values when it builds the invocation, not when the event was published. A persona or model switch that lands between publish and stamping stamps the newer value on the earlier event. The values also reflect the most recently constructed or switched runtime, which matches the best-effort cross-channel attribution of session_id.

Agent-class events report the process-level resolved model, which may differ from a session's switched model: an ACP session that switches model or persona updates only its own per-session context.

task_id is set only when an A2A task drives the turn. The TUI single-turn path, the stderr path, and the ACP path publish no A2A attribution, so task_id is null there.

The turn_completed usage fields are the turn's sums across its LLM calls, accumulated as each call completed. total_tokens is the sum of the per-call totals, each the wire's total or input + output when the wire omitted it; it is null only when no call reported a total. cost is the sum of the reported per-call costs and is null when none was priced. cost_complete is the AND of the per-call flags, so a sum with one incomplete component is a lower bound. duration_ms is the turn's wall-clock span.

The session_ended usage fields are the session's cumulative sums across every turn it ran, with the same fallback and completeness conventions. They reset when the runtime switches sessions, so the totals cover the session that ended only. Compaction never resets them: it shrinks the context, not the billing total.

agent_switched and model_switched report a switch that already happened. Their payloads hold two values: from is the value in use before the switch, to is the value now active. agent_switched carries persona slugs, and its from is null when the session had no persona. model_switched carries provider/model identities, and its from is always present. Re-selecting the current value is still a switch, so it reports from equal to to. Both envelopes are stamped after the switch, so their agent and model fields report the new state.

Session id

The runner tracks the session id from SessionEvent::Started and SessionEvent::Switched on the session bus. The envelope carries the tracked id.

The id is an empty string in two cases:

  • The runtime published no session event. Stderr mode and TUI single-turn publish none, so their turn and tool envelopes carry "".
  • The event is agent-class. Agent events are process-scoped, so agent_started and agent_shutdown always carry "". This is by design.

The switch events are session-class, so agent_switched and model_switched carry the tracked session id like every other session event.

Ordering

The agent guarantees order in two scopes:

  • Within one [[hooks]] entry on one runner. The entry has one subscriber task per runner. It runs one handler to completion before it takes the next event, so a hook never overlaps itself.
  • Within one event channel. Events on one channel arrive in publish order. turn_started and turn_completed share the turn channel, so turn_started always precedes turn_completed.

Order across channels is best-effort. A tool_started and a turn_completed that are both ready can arrive in either order. A hook that declares both session-class and agent-class events runs on two runners, so its agent_started and turn_started have no relative order.

The switch events share the session channel with the session lifecycle events, so they are ordered against them. A persona switch whose model override takes effect emits agent_switched before model_switched: two user-meaningful facts changed, so a hook sees two invocations.

Failure behavior

A hook failure never affects the agent run.

  • A handler that exits non-zero, fails to spawn, or exceeds timeout_ms produces one warning log line: hook '<name>' failed on <event>: <error>.
  • The warning goes to the agent log file in {state base}/nu-agent/logs/ (see Log file). The agent never writes log output to the terminal.
  • A timeout kills the subprocess.
  • The agent never retries a failed hook.
  • The agent never publishes a hook result.
  • The turn continues.

At exit the agent gives a running handler limited grace:

  • Agent-class runners: one 2 s budget shared by every runner, so a hook that hangs never holds exit past it.
  • Session-class runner in stderr mode: one 250 ms pause in total, after the turn.
  • Session-class runner in TUI and ACP: no exit wait. A handler still running when the process exits is abandoned.

session_started and session_ended are per-session events. They fire where a session lifecycle exists: the TUI interactive loop and ACP sessions. Stderr mode and TUI single-turn run one turn and publish no session lifecycle event.

permission_requested fires where the agent prompts the user: TUI and ACP. Stderr mode resolves permissions by policy and never prompts, so it never fires there.

permission_decision_timed_out fires where a permission card can time out. In TUI single-turn the request is published but no card consumer runs, so the request waits out its decision timeout and the event fires there too. Stderr mode never prompts, so it never fires there.

permission_decision_submitted fires where a decision reaches the permission resolver. In TUI single-turn the resolver is installed but no card consumer runs, so no decision is ever submitted and the event never fires there. Stderr mode never prompts, so it never fires there either.

permission_decision_ignored fires where a submitted decision can outlive its request. In TUI single-turn the resolver is installed but no card consumer runs, so no decision is ever submitted and the event never fires there. Stderr mode never prompts, so it has no decision submission path and the event never fires there either.

permission_request_cancelled fires where a permission prompt can be open when the turn is cancelled. In TUI single-turn the resolver is installed but no card consumer runs and no cancel handling exists, so no cancel reaches the resolver while a request is pending and the event never fires there. Stderr mode never prompts, so it never fires there either.

permission_auto_resolved fires where the policy resolves a tool call without prompting. That is every tool call in stderr mode, and every non-asked call in TUI interactive, TUI single-turn, and ACP mode. It is the only permission event that fires in stderr mode. The event fires once per policy-resolved call, so a hook that declares it runs one subprocess per call; the subprocess spawns only when the hook declares the event.

compaction_started and compaction_completed fire where compaction runs. The chain's threshold decision fires in every mode, but only two modes consume the request: the TUI interactive loop dispatches it through the orchestrator, for both auto threshold compaction and /compact, and an ACP session runs it post-turn, after the turn's drain ends and inside a second drain, so the client sees the events. Stderr mode and TUI single-turn run run_single_turn, which bypasses the orchestrator loop: the turn pipeline still publishes the compaction request, but nothing dispatches it, so no compaction runs there. compaction_failed is the exception: the turn pipeline's store-open failure and its session-load failure emit it in every mode, even where no compaction attempt runs.

compaction_completed carries the summary preview only: the full summary body is unbounded and stays out of the envelope. The streamed CompactionSummaryChunk is not a hook event, because one subprocess per streamed chunk is unbounded volume.

agent_started and agent_shutdown are per-process events. They fire exactly once per process in all three modes. The pair is best-effort on signals: no SIGTERM handler exists, so SIGTERM and SIGKILL produce no agent_shutdown.

agent_switched fires on a user-initiated agent switch: the TUI agent picker and the ACP agent config option. model_switched fires on a user-initiated model switch: the TUI model picker and the ACP model config option. Neither fires in stderr mode, TUI single-turn, or the plugin, because none of them has a switch path. A persona switch whose model override takes effect emits agent_switched before model_switched on the same channel, because two user-meaningful facts changed. In ACP the startup default-agent load is not a switch, and it publishes before the session hook runner subscribes, so no hook observes it.

The plugin agent command runs turns but starts no hook runner. Hooks never fire there. The agent binary does start the runners. See Example: signal an external app.

Example: signal an external app

This script posts each turn boundary to a local HTTP endpoint. Save it as $XDG_CONFIG_HOME/nu-agent/hooks/herdr.nu.

# ~/.config/nu-agent/hooks/herdr.nu
const HERDR_URL = "http://127.0.0.1:7777/events"

def turn_started [event: record] {
    let body = {
        kind: "turn_started"
        session: $event.session_id
        prompt: $event.payload.prompt
    }
    http post --content-type application/json $HERDR_URL ($body | to json)
}

def turn_completed [event: record] {
    let body = {
        kind: "turn_completed"
        session: $event.session_id
        tool_calls: $event.payload.tool_calls
    }
    http post --content-type application/json $HERDR_URL ($body | to json)
}

Register it in config.toml:

[[hooks]]
name = "herdr"
events = ["turn_started", "turn_completed"]
script = "hooks/herdr.nu"
timeout_ms = 5000

Run one turn with the agent binary:

^agent "list the rust files"

The caret forces the external agent binary. With the plugin registered, agent alone calls the plugin command, which starts no hook runner. The binary runs one turn in stderr mode, where the runners are wired.

The endpoint receives one turn_started post and one turn_completed post. If the endpoint is down, http post fails, the handler exits non-zero, and the agent logs one warning. The turn still completes.

Deferred

Hooks cannot veto or modify an event. Hooks run without a sandbox. There is no /hooks panel. The agent spawns one process per event; a persistent-stdio mode is not implemented.

Log file

The agent logs to a file only; it never writes log output to the terminal.

  • The target is this instance's own file in {state base}/nu-agent/logs/ — $XDG_STATE_HOME/nu-agent/logs/ by default, and nu-agent-dev instead of nu-agent in a debug build. See Paths for the full ladder.
  • The file name names the instance: agent-{name}-{pid}.log, and agent-{pid}.log without a name. {name} is the --name value. The pid is always part of the name, so two same-named instances never interleave into one file. A name becomes a file name part, so characters outside A-Z a-z 0-9 . _ - become -.
  • The role is recorded in the file's header lines, never in its file name: tui for the default route (TUI, TTY, and single-prompt runs), a2a for the A2A server, acp for the ACP server, and run for the one-shot subcommands and the plugin's pipeline runs. The header also carries the name when the run has one, the pid, and the RFC 3339 start time.
  • The TUI shows the full path of its own instance file in the Status panel (/status), as a Log: row. That path is the file the run writes, so no directory listing is needed to find it.
  • NU_AGENT_STATE_HOME applies from process start: the environment is readable before config.toml loads, so the log directory is correct from the first line, with no re-initialization.
  • A [paths].state_home value in config.toml applies only after the config file is loaded: the sink swaps to {value}/nu-agent/logs/ at that point and keeps the instance's own file name.
  • In the pre-load window — the first few startup lines — the log goes to the derived default, i.e. $XDG_STATE_HOME's tree or ~/.local/state.
  • Logging is always on: no flag is required, and the file is the only target.
  • RUST_LOG and --log-level set the filter; the default is info. warn and above always reaches the file, whatever the filter asks for.
  • Each instance keeps its own file, appended run after run. A second instance starting never rotates, truncates, or collects the file another instance is writing.
  • At open the store keeps the newest 20 instance files. Three files are never collected: the opening instance's own file, a file modified within the last hour, and a file the platform refuses to remove. A writer that froze still leaves a recent trail, so that trail survives.
  • When the state ladder does not resolve or the instance's file cannot open, the log goes to {temp dir}/nu-agent-log-{pid}.log with the reason as its first line, and the run continues.
  • On quit and on a panic, the last 500 lines are appended to the file as a ring dump block.

MCP Authentication Commands

Manage OAuth credentials for MCP servers. These commands operate on the credential store (not config.toml).

agent mcp auth login

Triggers the OAuth authorization-code flow with PKCE for a configured MCP server. Opens a browser to the server's authorization URL and waits for the callback.

The MCP server must be configured with auth.type = "oauth" in config.toml. On success, tokens are saved to the credential store and automatically refreshed on expiry.

Example output (stderr):

Opening browser to authenticate with MCP server 'my-server'...
If the browser doesn't open, visit:
  http://auth-server.example.com/authorize?response_type=code&client_id=...
Successfully authenticated with MCP server 'my-server'

What happens during login

The OAuth authorization-code flow with PKCE proceeds as follows:

  1. Load config — reads the MCP server configuration from config.toml.
  2. Start callback server — binds a local HTTP server to 127.0.0.1 on a random port to receive the OAuth redirect.
  3. Discover OAuth metadata — fetches /.well-known/oauth-authorization-server from the server URL to find authorization, token, and registration endpoints.
  4. Register client — if no client-id is configured, performs dynamic client registration via the discovered registration endpoint. If client-id is configured, uses it directly.
  5. Generate PKCE challenge — creates a cryptographically random code_verifier and code_challenge (SHA-256 hashed) for the authorization request.
  6. Build authorization URL — constructs the URL with response_type=code, client_id, redirect_uri, scope, state (CSRF token), and code_challenge.
  7. Open browser — launches the system browser to the authorization URL.
  8. User authenticates — the user logs in and grants consent in the browser.
  9. Browser redirects — the authorization server redirects to the callback server at http://127.0.0.1:<random-port>/mcp/oauth/callback?code=...&state=....
  10. Validate state — the callback server verifies the state parameter matches the one sent (CSRF protection).
  11. Exchange code for tokens — sends the authorization code, code_verifier, and redirect_uri to the token endpoint. Receives access_token, refresh_token, and expires_in.
  12. Save credentials — stores the tokens in the OS keychain. When no keychain is available, the agent uses its file store instead.
  13. Stop callback server — shuts down the local HTTP server.

On subsequent agent runs, the stored access token is used automatically. If expired, the refresh token is used to obtain a new access token without user interaction.

agent mcp auth logout

Clears stored OAuth tokens and client registration data for a server. Does not modify config.toml.

agent mcp auth logout my-server

Example output:

If no credentials are stored for the server:

No stored credentials for 'my-server'

Output contract

  • stdout: final machine-readable Nushell record output only.
  • stderr: interactive UX/progress output (spinner while busy, tool progress, warnings, completion).

This keeps pipelines stable while preserving interactive feedback.

TUI transcript markdown and fenced code

When running in TUI mode, assistant markdown is projected into transcript-friendly lines. Each markdown element maps to a dedicated style. Colors are named; the concrete RGB values come from the active theme (--theme, default catppuccin-mocha).

Busy indicator behavior

  • Busy state is shown via spinner on interactive TTY stderr.
  • Default UX does not print redundant persistent busy lines like "thinking" or "response ready".
  • Default tool lifecycle UX is concise and singular:
    • busy: [spinner] tool <tool_name> args=<truncated_args> while running
    • completion: ✓ tool <tool_name> args=<truncated_args> or ✗ tool <tool_name> args=<truncated_args> exactly once
    • result payload follows on next line(s) as a separate block when meaningful
  • Concise levels print non-empty payloads verbatim (including null, [], and {}).
  • In non-interactive stderr (non-TTY), spinner is disabled and only policy-driven persistent lines are shown.
